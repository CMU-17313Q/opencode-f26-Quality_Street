# Traceability: Hamad Alhajri (halhajri)

**Target feature:** opencode permission rules. A tool call (for example a bash command) is matched against the user's `allow` / `ask` / `deny` rules, which can use wildcard patterns such as `git *` or `rm *`.

**Main source files:**
- `packages/opencode/src/permission/index.ts` (rule evaluation, ask / allow / deny handling)
- `packages/opencode/src/permission/command.ts` (how one shell command is turned into the text that rules are matched against; added in P4B)
- `packages/core/src/util/wildcard.ts` (wildcard matching)
- `packages/opencode/src/tool/shell.ts` (splits a shell command into its parts and asks for permission)

## Requirement changes

| ID | Original requirement (P4A) | Revised requirement | Why it changed |
|---|---|---|---|
| R1 | When a command matches several rules, the last matching rule in the config decides the outcome. | Removed. | This was the example row from the P4A template and I left it in my table by mistake. It cites C-12, which does not exist in my notes, so it has no interview evidence. It also conflicts with my original R3 ("order does not change the result"). |
| R2 | A deny rule also blocks the command when it is run with sudo or as part of a longer chained command. | A deny rule blocks the command when it is run directly, with `sudo` in front of it (with or without sudo options), or as one part of a longer chained command. Each command in a chain is checked on its own. | Checkability and feasibility. "Part of a longer command" did not say how far it goes. O-3 also wanted base64 tricks and scripts that run `rm` inside them to be caught. That is not feasible: opencode sees the text of the command, not what a script or an encoded string will do when it runs. The revised wording keeps what all three interviewees asked for (sudo and chained commands) and states it so that a test can check it. |
| R3 | The order of the rules in the config does not change the result. | The result for a command is decided by the last rule in the config that matches it. Rules that do not match a command never change its result, wherever they are placed. A deny rule written after an allow rule always wins, even when the allow rule is more specific. | Conflict and feasibility. The interviewees did not agree on what should replace order: C-7 wanted the more specific rule to win, so `git status` allow beats `git *` ask, while S-7 and O-7 wanted deny to always win, even over a more specific allow. Order also cannot be removed from opencode: default rules, the user's config, and always-allow choices are joined into one list, and a later rule overriding an earlier one is how a user changes a default. The original R3 property failed for this reason (see Test Execution and Triage). The revised requirement keeps what the users needed: the result is predictable from one simple rule, unrelated rules can be moved freely, and there is a guaranteed way to make a deny win. |
| R4 | Extra spaces and extra options do not change which rule a command matches. | Extra spaces or tabs between the words of a command, and extra options added after the words that a rule ending in ` *` names, do not change which rule the command matches. | Checkability. "Extra options" did not say where the option goes or which rules it applies to. A rule without a wildcard, such as `git status`, is an exact match and is supposed to stop matching when something is added. I also left letter case out, because the interviewees disagreed: C-6 said `Git status` is a different command, and O-6 said a capital letter should not get around a rule. |
| R5 | When a rule or an always allow choice is removed, the change applies to the next command in the same session, without a restart. | When a rule is removed from the config, the next command is decided exactly as if the rule had never been added, with no restart. Always-allow choices are a separate layer on top of the config, so when that layer is cleared the command is decided by the config again. | Feasibility. opencode has no action for removing a single always-allow choice. The choices are kept in memory for the running instance and are never written to the config. Building a way to remove one needs new UI and a new server action, which is outside rule matching. The revised wording keeps the user need from C-4, S-4 and S-5 (no old rule keeps working, and nothing is remembered from before) in a form that the current code can be checked against. |

## Test Execution and Triage

Eight property-based tests were written with `fast-check` for R2, R3, R4, and R5. Three of the first properties failed.

| Requirement | Shrunk counterexample | Outcome | What I did |
|---|---|---|---|
| R2 | Rules `*` allow, `git *` deny. The command `sudo git` was allowed. | Code bug | The shell tool matched rules against the whole text `sudo git`, which does not start with `git`. I added `ShellCommand.sudo` in `packages/opencode/src/permission/command.ts`. It finds the command behind `sudo`, skipping sudo options such as `-u root`, and the shell tool now also checks that command against the rules. |
| R4 | Rule `curl *` allow. `curl status` was allowed, but `curl`, a tab, then `status` fell through to the default and asked. With `*` allow and `git push *` deny, `git`, two spaces, `push origin` was allowed. | Code bug | Patterns are written with single spaces, and the shell tool passed the command text as typed. I added `ShellCommand.normalize`, which turns spaces and tabs between words into one space and leaves quoted text alone. The shell tool now applies it before matching. |
| R3 | Rules in this order: `ls push *` allow, `git status *` allow, `*` ask. The command `ls push` asks, because `*` ask is the last rule that matches. With the same three rules reordered so that `ls push *` allow comes last, `ls push` is allowed. | Requirement problem | The code decides by the last matching rule on purpose. The original R3 was not feasible and the interviewees conflicted on what should replace order, so I revised R3 (see Requirement changes) and rewrote the property as three properties for the revised wording. |

R5 passed the first time.

After the fixes, all eight properties pass, and the existing permission and shell tool tests still pass.
