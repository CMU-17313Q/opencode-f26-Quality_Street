## Requirement changes

| ID | Original requirement (P4A) | Revised requirement | Why it changed |
|---|---|---|---|
| R1 | For an assertion failure, "Where to look" names the function the test called, not only its file, so the student knows what to read. The acceptance criteria say it "lists src/grades.ts and names letterGrade". | For an assertion failure, "Where to look" names the function that the failing test line calls, next to the test location, as well as listing the files the test imports, so the student knows what to read. | Feasibility. The original wording reads as if the tool says which file defines the function. The tool only sees the test output and the test file, so to find the defining file it would have to read and parse every imported file. That means reading more of the student's code than the tool asks permission for today, and it fails when a function is re-exported or comes from a package. What the interviewees wanted, knowing where to look (S-9, O-13), is met by naming the called function and the test line next to the imported files. |
| R2 | The report describes the failure and asks questions. It never gives replacement code, and it does not explain how the student's code works. Acceptance: "Questions to investigate asks the student to work things out and does not tell them what to change." | The report describes the failure and asks questions. It contains no code block and no code other than values taken from the failing run, so it cannot contain replacement code. Every hint under "Questions to investigate" poses a question. | Checkability, and a conflict with R5. "Does not explain how the student's code works" and "does not tell them what to change" cannot be decided by a program, so no property can check them. The revised wording keeps what S-20 and C-2 asked for (no fix handed over, no long explanation) as three checks a program can do: no fenced code, only expected inline code, and every hint is a question. It also removes the conflict with R5, whose level 2 shows a snapshot of the student's own code: R2 now describes the default report and R5's snapshot is the student's existing source, shown only when asked. |
| R7 | The student can choose between two modes: quick, which is today's report, and interactive. Interactive shows the failure and a snapshot of the code, then asks which line is responsible, and holds back the explanation until the student answers or asks to continue. | Interactive mode is level 2 of R4 without the explanation sections: it shows the failure and a snapshot of the code, then asks which line is responsible. The student's answer is handled as a separate follow-up (R8). | Conflict and feasibility. R4 (levels) and R7 (modes) are two switches that both decide how much of the report is shown, and they described different contents for the same situation. Also, a tool call runs once and returns, so it cannot "hold back the explanation until the student answers". Making interactive a level of R4, with the answer handled in R8, keeps what C-1, C-3 and C-5 asked for (a question first, and a choice) in a form that can be built. |

R3, R4, R5, R6 and R8 are kept as written: each describes behavior that can be built and checked with the tool's inputs and outputs.

## Test Execution and Triage

Run with `cd packages/opencode && bun test test/tool/test-failure.property.test.ts test/tool/test-failure.test.ts`.

Six properties were written (R1, R2, R3 twice, R6 twice). The first run, with a placeholder for the new function-name lookup, gave these results:

1. **R1 failed** with the counterexample `module: "grades", fn: "aAaFn", args: ""` (one assertion, `expect(aAaFn()).toBe(4)`): "Where to look" listed no function. This is the "New: fails today" case from P4A, so it is a **code gap**. I added `calledFunction()` and `calledFunctions()` to `test-failure.ts`, which read the failing line of the test file the tool already reads, and `whereToLook()` now adds a line naming the function.
2. **R2 failed** on an `assertion` failure with no optional data. My property required every hint to *end* with `?`, but the real hint is "Which function produced the received value? Work out by hand what it should return...", a question followed by an instruction. That is what R2 asks for, so it was a **wrong test**. I changed the property to require that every hint contains a question.
3. **R2 failed again** with the test name `` ` `` (one backtick). The report prints test names unchanged in the `## 1. name` heading, and P4A already allows the test name as inline code, so an unbalanced backtick in a name broke my span-matching. It was a **wrong test**: the property now checks for a real fence at the start of a line and reads code spans from the lines below the headings.
4. **R2 failed a third time** with a failure of kind `unknown`. Its only hint was "Read the first error message in the output and follow the stack trace to the first file from your own project." That is an instruction, not a question, in a section called "Questions to investigate". It was a **code bug** against the revised R2. I reworded it to "What is the first error message in the output, and which is the first file from your own project in its stack trace?"
5. R3 (both properties) and R6 (both properties) passed the first time.

**Final local results:** 19 pass, 0 fail across `test-failure.property.test.ts` (6 properties) and `test-failure.test.ts` (12 existing tests plus 1 new end-to-end test); the 2 tests of `test-failure-command.test.ts` also pass; `bun run typecheck` is clean.

Checks that the properties are not flaky and can fail: the 6 properties passed in 8 reruns with fresh random seeds. Two deliberate bugs, each tried once by hand and then reverted (removing the Scope section, and naming the wrong function), were each caught by exactly the property written for that requirement (R6 and R1).
